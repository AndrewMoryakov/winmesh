<h1 align="center">winmesh</h1>

<p align="center"><b>Назовите машину — и запускайте на ней PowerShell: один конфиг, два штатных транспорта (WinRM или SSH), в ответ — настоящие объекты, в любой сети. Плюс проверки канала, ограничение файрвола для WinRM, локальное хранилище учётных данных и необязательные установщики SSH-сервера. Для админов и разработчиков, у которых несколько Windows-компьютеров — и Linux- и macOS-машины рядом с ними.</b></p>

<p align="center"><a href="README.md">English</a> | <b>Русский</b></p>

```powershell
Invoke-WinMeshCommand workstation-01 { hostname; whoami }     # выполнить команду на хосте по имени
Test-WinMeshFleet                                             # проверить сразу все хосты из конфига
```

winmesh — небольшой PowerShell-модуль для связи Windows-машин по PowerShell Remoting **или SSH**. Вы один раз описываете машины в конфиге; дальше называете хост, запускаете на нём команду и получаете обратно настоящие объекты. Контроллер и цели могут быть на Windows, Linux или macOS: WinRM — между Windows-машинами, SSH — везде; см. [Платформы](#платформы).

В модуле девять команд. Четыре запускают и проверяют (`Invoke-WinMeshCommand`, `Test-WinMeshHost`, `Test-WinMeshFleet`, `Get-WinMeshConfig`), три готовят WinRM-путь (`New-WinMeshBootstrap` для цели, `Register-WinMeshCredential` и `Connect-WinMeshHost` для контроллера), а две показывают и меняют, каким сетям разрешено обращаться к порту WinRM хоста (`Get-`/`Set-WinMeshFirewallScope`). Два необязательных отдельных скрипта устанавливают SSH-сервер на цель под Windows или Linux. Агентов нет, зависимостей нет — только PowerShell и, для SSH, клиент `ssh`.

Это небольшой модуль до версии 1.0 (0.2.1), рассчитанный на несколько машин, а не на большие парки и не на управление конфигурацией; автоматического набора тестов в репозитории нет — проверки ручные, они описаны в [CONTRIBUTING.md](CONTRIBUTING.md). См. [Статус и известные ограничения](#статус-и-известные-ограничения).

## Простыми словами

### Проблема

Когда у вас больше одного компьютера, постоянно хочется что-то сделать на другом: проверить службу, прочитать лог, скопировать файл, посмотреть, включён ли он вообще. Инструменты для этого есть (PowerShell Remoting, SSH), но у каждого свои шаги настройки и ловушки, на которые легко наступить и которые долго диагностировать: удалённую сторону должен включить локальный администратор, порт файрвола открыт шире, чем вы думаете, аутентификация откатывается к неожиданному режиму, а SSH отдаёт текст вместо объектов PowerShell, да ещё и с правилами квотирования, разными в разных оболочках.

### Для кого

Для тех, у кого несколько машин — рабочие станции, NAS, лабораторные стенды, пара хостов на Linux или macOS — и кто хочет обращаться к ним по короткому имени из одного места, в какой бы сети они ни были связаны (Tailscale, NetBird, ZeroTier или обычная LAN). Для тех, кому Ansible слишком тяжёл для такой задачи. Опытные пользователи получают транспорт на каждый хост и область файрвола, проверку состояния со структурированным результатом, пригодным для скриптов, и транспорт, внутреннее устройство которого описано ниже.

### Что вы получаете

- **Один способ сказать «выполни это там».** `Invoke-WinMeshCommand <имя> { ... }` работает одинаково и по WinRM, и по SSH; транспорт — одно поле конфига на хост.
- **Объекты, а не текст.** Результат приходит как объекты PowerShell, которые можно передавать по конвейеру и фильтровать, в обоих транспортах.
- **Любая сеть.** winmesh нужны лишь стабильные, взаимно достижимые адреса, а не какая-то конкретная сеть: Tailscale, NetBird, ZeroTier или обычная LAN работают одинаково.
- **Карта ваших машин.** Один `config/hosts.psd1`: короткое имя, адрес и (для WinRM) id учётных данных на каждый хост, плюс значения по умолчанию, которые можно переопределить для хоста.
- **Знать заранее.** `Test-WinMeshHost` и `Test-WinMeshFleet` проверяют всю цепочку — порт, ответ, учётные данные, реальную команду, уровень привилегий — и возвращают структурированный результат, по которому могут принимать решения скрипты.
- **Более узкая открытость WinRM.** Bootstrap-скрипт ограничивает порт WinRM перечисленными вами подсетями, а `Get-`/`Set-WinMeshFirewallScope` позже показывают и заново применяют это ограничение, с защитой от самоблокировки.
- **Локальное хранилище учётных данных.** Учётные данные WinRM шифруются DPAPI и хранятся вне git.
- **Уроки уже встроены.** Длинный список подводных камней WinRM, файрвола, SSH-квотирования и локализации учтён в скриптах и [записан](#встроенные-грабли).

### Чем он не является

- Не новый протокол и не агент: под капотом — штатный WinRM с `Invoke-Command` либо штатный `ssh`.
- Не управление конфигурацией и не для больших парков (для этого Ansible или DSC). Проверки парка идут хост за хостом, а не параллельно.
- Не способ обойти первый админ-шаг: чтобы включить WinRM, нужен локальный администратор на цели, поэтому модуль лишь генерирует скрипт.
- Не менеджер секретов для SSH: он никогда не запрашивает, не хранит и не пересылает SSH-ключ или пароль (`BatchMode=yes`).
- Не WinRM с Linux или macOS: этот путь требует Windows-контроллер. Там используйте SSH.
- Не установщик SSH-сервера, встроенный в модуль: необязательные скрипты — отдельные, и модуль их никогда не вызывает.

### Глоссарий

| Термин | Что означает здесь |
|---|---|
| **Контроллер** | Машина, *с которой* вы запускаете winmesh (ваш ноутбук). Здесь лежат конфиг и хранилище учётных данных. |
| **Цель** | Машина, до которой нужно достучаться. На ней работает WinRM-listener или SSH-сервер. |
| **Запись хоста** | Одна машина в `config/hosts.psd1`: короткое имя, адрес и настройки транспорта. |
| **Транспорт** | Как winmesh добирается до хоста: `winrm` (по умолчанию) или `ssh`, задаётся для каждого хоста. Всё поверх транспорта одинаково. |
| **WinRM / PowerShell Remoting** | Встроенный в Windows канал удалённого управления (здесь — HTTP, порт 5985), управляется через `Invoke-Command`. |
| **Bootstrap** | Одноразовый скрипт, который вы запускаете на цели от администратора, чтобы включить WinRM и сузить её файрвол. |
| **Оверлейная сеть** | VPN-подобная сеть (Tailscale, NetBird, ZeroTier), дающая машинам стабильные адреса, где бы они ни находились. |
| **`AllowedSubnets`** | Список исходных сетей, которым разрешено обращаться к порту WinRM хоста. По умолчанию `100.64.0.0/10` — общий диапазон Tailscale и NetBird. |
| **TrustedHosts** | Клиентский список WinRM; при подключении по IP-адресу цель должна быть в нём, потому что Kerberos не применяется. |
| **DPAPI** | Средство Windows, шифрующее сохранённые учётные данные так, чтобы их мог прочитать только ваш аккаунт на этом контроллере. |

## Что внутри

Всё перечисленное здесь реализовано в этом репозитории; ничего не помечено как экспериментальное или запланированное. Пункты с пометкой **только WinRM** требуют Windows-контроллер и WinRM-хост.

### Адресация и конфигурация

- **Хосты по имени в одном файле.** `config/hosts.psd1` (файл данных PowerShell, разбирается без выполнения кода) перечисляет хосты и значения по умолчанию; значения хоста переопределяют умолчания; `$env:WINMESH_CONFIG` или `-Config` выбирает другой файл. `Get-WinMeshConfig` загружает и проверяет его. → [Справочник по конфигу](#справочник-по-конфигу)
- **Старый ключ по-прежнему понимается.** Устаревшее значение по умолчанию `TailscaleCidr` читается как `AllowedSubnets`, если `AllowedSubnets` не задан. → [Справочник по конфигу](#справочник-по-конфигу)

### Запуск команд

- **`Invoke-WinMeshCommand`.** Выполняет scriptblock на именованном хосте, с `-ArgumentList`, и возвращает объекты. → [Примеры использования](#примеры-использования)
- **Два взаимозаменяемых транспорта.** `winrm` (по умолчанию) использует `Invoke-Command` с сохранённой учёткой; `ssh` использует системный клиент `ssh`: нагрузка упакована в один токен base64, а результат сериализуется тем же движком CliXml, что и удалённое взаимодействие PowerShell. → [SSH](#ssh-вместо-winrm)
- **Смешанные парки.** В одном конфиге — хосты на Windows, Linux и macOS; SSH работает во всех направлениях. → [Платформы](#платформы)

### Проверка состояния

- **`Test-WinMeshHost` / `Test-WinMeshFleet`.** Читаемый отчёт плюс объект результата (`Host`, `Address`, `Transport`, `Ok`, `Checks`); `-Quiet` — для автоматизации. Набор проверок зависит от транспорта. → [Test-WinMeshHost подробно](#test-winmeshhost-подробно)
- **SSH-баннер.** SSH-проверка читает баннер сервера, поэтому видно, какой именно SSH-сервер ответил. → [Грабли](#встроенные-грабли)

### Подготовка машин

- **Bootstrap цели (WinRM).** `New-WinMeshBootstrap` генерирует скрипт из четырёх шагов: включить PowerShell Remoting, сузить порт 5985 до `AllowedSubnets`, выдать полный админ-токен локальным учёткам в удалённых сессиях, вывести факты для вашего конфига. → [Настройка](#настройка--шаг-за-шагом)
- **Хранилище учётных данных (только WinRM).** `Register-WinMeshCredential` сохраняет учётные данные, зашифрованные DPAPI, на каждый id. → [Хранилище учётных данных](#хранилище-учётных-данных)
- **Настройка контроллера (только WinRM).** `Connect-WinMeshHost` запускает локальную службу WinRM и добавляет цель в `TrustedHosts`; поддерживает `-WhatIf`. → [Настройка](#настройка--шаг-за-шагом)
- **Установщики SSH-сервера (необязательные).** Отдельные скрипты, которые устанавливают и запускают OpenSSH на цели под Windows или Linux, ограничив TCP/22 переданными вами диапазонами. → [Установка SSH-сервера](docs/ssh-server-setup.md) (на английском)

### Управление сетевой открытостью

- **`AllowedSubnets`.** Одна настройка (общая, переопределяется для хоста), определяющая, каким исходным сетям доступен WinRM. → [Выбор разрешённых подсетей](#выбор-разрешённых-подсетей)
- **`Get-WinMeshFirewallScope` / `Set-WinMeshFirewallScope` (только WinRM).** Сравнивают действующее правило с конфигом и применяют конфиг заново; защита отказывается от изменения, которое отрезало бы вашу собственную живую сессию, если не указан `-Force`; `-WhatIf` показывает предпросмотр. → [Область файрвола](#просмотр-и-изменение-того-каким-сетям-разрешено-подключаться)
- **Заметки по безопасности.** Почему границей служит оверлей, а диапазон файрвола — второй слой. → [Заметки по безопасности](#заметки-по-безопасности)

### Знания, которые не придётся открывать заново

- **Грабли.** Ловушки WinRM, файрвола, SSH, локализованной Windows и Linux/macOS из реальной отладки, встроенные в скрипты и перечисленные. → [Встроенные грабли](#встроенные-грабли)
- **Таблица диагностики.** Симптом, причина, что делать — для ошибок, которые выдаёт сам модуль. → [Диагностика](#диагностика)

### Не реализовано (по замыслу или пока)

Нет управления конфигурацией, параллельного запуска на всём парке, работы с SSH-ключами и паролями, WinRM с Linux/macOS и обработки HTTPS (порт 5986) — см. [чего он намеренно не делает](#чего-он-намеренно-не-делает) и [Статус и известные ограничения](#статус-и-известные-ограничения).

## Как это работает

<p align="center">
  <img src="docs/assets/winmesh-how-it-works.png" alt="winmesh: контроллер находит имя хоста в конфиге и обращается к машине по WinRM или SSH" width="100%">
</p>

1. **Назовите машины.** Опишите каждую цель — короткое имя, адрес, id учётных данных (WinRM) или настройки SSH — в `config/hosts.psd1`.
2. **Подготовьте один раз.** Для WinRM-цели запустите на ней сгенерированный bootstrap-скрипт, а на контроллере — `Connect-WinMeshHost`. SSH-цели нужен только SSH-сервер.
3. **Запускайте по имени.** `Invoke-WinMeshCommand <имя> { ... }` выбирает транспорт хоста — `winrm` или `ssh` — и выполняет там ваш scriptblock.
4. **Получайте объекты.** Результат возвращается как объекты PowerShell, которые можно передавать дальше по конвейеру.

Один раз настраиваете каждую машину, а дальше просто вызываете `Invoke-WinMeshCommand <имя> { ... }`.

| Шаг | WinRM-хост | SSH-хост |
|---|---|---|
| Подготовка цели | bootstrap-скрипт, один раз от администратора | SSH-сервер (+ PowerShell 7 на Linux/macOS), см. [установку SSH-сервера](docs/ssh-server-setup.md) |
| Подготовка контроллера | `Register-WinMeshCredential`, `Connect-WinMeshHost` (только Windows) | не нужна — клиент `ssh` аутентифицируется сам |
| Запуск | `Invoke-Command -ComputerName <адрес> -Credential <сохранённая>` | `ssh ... <оболочка> -EncodedCommand <base64>` |
| Результат | объекты от удалённого взаимодействия | объекты, восстановленные из CliXml |
| Проверка | порт 5985, WS-Management, учётные данные, команда, админ-токен | порт 22 + баннер, команда, админ-токен (Windows) или root/не root (Linux/macOS) |

## Быстрый старт

Из клона этого репозитория на **контроллере** (вашем ноутбуке). Права администратора нужны только для bootstrap на цели и для `Connect-WinMeshHost`. Каждый шаг подробно описан в разделе [Настройка — шаг за шагом](#настройка--шаг-за-шагом).

```powershell
git clone https://github.com/AndrewMoryakov/winmesh.git
cd winmesh
Import-Module .\winmesh.psd1

Copy-Item .\config\hosts.example.psd1 .\config\hosts.psd1
notepad .\config\hosts.psd1                       # добавьте свою машину (Address + Credential) и задайте AllowedSubnets

New-WinMeshBootstrap -OutFile .\bootstrap.ps1     # берёт AllowedSubnets из конфига; скопируйте на цель и запустите там один раз от имени администратора

Register-WinMeshCredential -Id 'admin@workstation-01'   # логин — ровно так, как его напечатал bootstrap
Connect-WinMeshHost -Name workstation-01                # настройка контроллера (админ, один раз)
Test-WinMeshHost    -Name workstation-01                # пять зелёных проверок = успех

Invoke-WinMeshCommand workstation-01 { hostname; whoami }
```

Создайте конфиг **до** генерации bootstrap-скрипта: `New-WinMeshBootstrap` берёт область файрвола из `AllowedSubnets` в `config\hosts.psd1`, а без конфига подставляет `100.64.0.0/10` (диапазон Tailscale/NetBird) — и контроллер в обычной LAN или ZeroTier окажется отрезан. Либо передайте `-AllowedSubnets` явно — см. [Выбор разрешённых подсетей](#выбор-разрешённых-подсетей).

Цели, доступные по **SSH**, полностью пропускают bootstrap, учётные данные и `Connect-WinMeshHost` — изменения WinRM им не нужны. См. [SSH вместо WinRM](#ssh-вместо-winrm).

## Требования для старта

- Windows PowerShell 5.1 **или** PowerShell 7 на Windows-машинах; PowerShell 7 (`pwsh`) на Linux и macOS — и на контроллере, и на целях. См. [Платформы](#платформы).
- Сеть, дающая машинам стабильные, взаимно достижимые адреса (Tailscale / NetBird / ZeroTier / LAN).
- Права администратора нужны ровно для двух шагов: `Connect-WinMeshHost` на контроллере и bootstrap-скрипт на каждой цели.

## Платформы

ssh-транспорт работает в любом направлении; WinRM требует Windows на обоих концах.

| Контроллер ↓ · Цель → | Windows | Linux / macOS |
|---|---|---|
| **Windows** (PowerShell 5.1 или 7) | `winrm` или `ssh` | `ssh` |
| **Linux / macOS** (PowerShell 7) | `ssh` | `ssh` |

**Почему WinRM остаётся Windows-к-Windows.** У PowerShell 7 на Linux/macOS нет
поддерживаемого WinRM-клиента (`Invoke-Command -ComputerName`, `Test-WSMan` и диск
`WSMan:` отсутствуют или зависят от стороннего стека PSWSMan/OMI), а хранилище
учётных данных — это DPAPI, который есть только в Windows: вне Windows
`Export-Clixml` записывает пароль простым hex. Поэтому на Linux/macOS-контроллере
`Register-WinMeshCredential`, `Connect-WinMeshHost`, `Invoke-WinMeshCommand` и
команды области файрвола отказываются работать с WinRM-хостом с понятным
сообщением, а `Test-WinMeshHost` / `Test-WinMeshFleet` показывают его как
проваленную проверку `WinRM client`, не прерываясь, — ssh-хосты смешанного парка
всё равно проверяются.

**Контроллер на Linux или macOS.** Установите [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell)
и пользуйтесь модулем так же, как в Windows. Путь к конфигу, `$env:WINMESH_CONFIG`
и `~/.ssh/config` работают как обычно; `CredentialStore` принимает любой разделитель.

```bash
git clone https://github.com/AndrewMoryakov/winmesh.git
cd winmesh
cp config/hosts.example.psd1 config/hosts.psd1     # хосты с Transport = 'ssh'
pwsh -c 'Import-Module ./winmesh.psd1; Test-WinMeshFleet'
```

**Цель на Linux или macOS.** Нужны SSH-сервер и PowerShell 7 — scriptblock
выполняется там в `pwsh`, и результаты по-прежнему приходят объектами. Задайте
хосту `SshShell = 'pwsh'`: значение по умолчанию `powershell` есть только в Windows.

```powershell
'linux-01' = @{
    Address   = '100.100.10.21'
    Transport = 'ssh'
    SshUser   = 'admin'
    SshShell  = 'pwsh'          # или полный путь, если PATH ssh-сессии его не видит
}
```

- **Linux:** установите `openssh-server` и [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-linux) из пакетов дистрибутива или Microsoft.
- **macOS:** включите *Удалённый вход* (Системные настройки → Основные → Общий доступ) и установите [PowerShell 7](https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-macos).
- Неинтерактивная ssh-команда не читает login-профили, поэтому её `PATH` может отличаться от вашего терминала. Если winmesh сообщает, что PowerShell не найден, укажите в `SshShell` полный путь, который печатает `command -v pwsh` на цели.

У Linux/macOS-цели в `Test-WinMeshHost` нет проверки *full admin token*: обычный
вход там — это норма, а root получают через `sudo`. Строка *command runs* говорит,
что именно, — например, `linux-01 / admin (Linux), not root`.

## Настройка — шаг за шагом

### Шаг 0 · Установите модуль (контроллер)

```powershell
git clone https://github.com/AndrewMoryakov/winmesh.git
cd winmesh
Import-Module .\winmesh.psd1
```

### Шаг 1 · Подготовьте каждую цель (выполняется НА цели, один раз, от администратора)

Цель становится доступной только после включения на ней WinRM, а для этого нужен **локальный администратор этой машины**. Удалённо обойти это невозможно: канала ещё не существует. Это единственный ручной шаг.

На **контроллере** сгенерируйте bootstrap-скрипт:

```powershell
New-WinMeshBootstrap -OutFile .\bootstrap.ps1
```

Скопируйте `bootstrap.ps1` на цель (RDP, флешка или GPO в домене) и запустите там **от имени администратора**. Скрипт:

1. включает PowerShell Remoting (`Enable-PSRemoting`);
2. сужает правило файрвола WinRM до ваших доверенных подсетей (см. [Выбор разрешённых подсетей](#выбор-разрешённых-подсетей));
3. выдаёт полный админ-токен локальным учётным записям в удалённых сессиях;
4. печатает данные о машине, нужные для конфига (имя компьютера, домен, точная строка логина).

Запомните напечатанное значение **LoginForCred** — оно понадобится на шаге 3.

> Bootstrap берёт `AllowedSubnets` из `config\hosts.psd1`. Если конфига ещё нет, он подставит `100.64.0.0/10` — сначала выполните шаг 2 или передайте `-AllowedSubnets` явно (см. [Выбор разрешённых подсетей](#выбор-разрешённых-подсетей)).
>
> Если цель уже доступна по WinRM или будет подключаться по SSH, пропустите этот шаг.

### Шаг 2 · Добавьте цель в конфиг (контроллер)

```powershell
Copy-Item .\config\hosts.example.psd1 .\config\hosts.psd1
notepad .\config\hosts.psd1
```

Заполните по одной записи на каждую машину:

```powershell
Hosts = @{
    'workstation-01' = @{
        Address    = '100.100.10.11'          # её адрес в оверлее/LAN или DNS-имя
        Credential = 'admin@workstation-01'   # любой id; используется на шаге 3
    }
}
```

### Шаг 3 · Сохраните учётные данные (контроллер)

```powershell
Register-WinMeshCredential -Id 'admin@workstation-01'
```

Появится запрос. Введите логин ровно в том виде, как его напечатал bootstrap:

- доменная машина → `DOMAIN\user`
- рабочая группа / отдельная машина → `COMPUTERNAME\user` (например, `workstation-01\admin`)

Пароль шифруется DPAPI — файл может прочитать только *ваша* учётная запись на *этом* контроллере. Если его скопировать в другое место, он бесполезен.

### Шаг 4 · Подготовьте контроллер (нужен админ, один раз)

```powershell
Connect-WinMeshHost -Name workstation-01
```

Команда запускает службу WinRM на контроллере и добавляет цель в `TrustedHosts` (нужно для аутентификации по IP). Выполняется один раз для каждого нового адреса цели.

### Шаг 5 · Проверьте

```powershell
Test-WinMeshHost -Name workstation-01
```

Ожидайте пять зелёных проверок: порт, WS-Management, учётные данные, команда выполняется, полный админ-токен.

### Шаг 6 · Пользуйтесь

```powershell
Invoke-WinMeshCommand workstation-01 { hostname; whoami }
Invoke-WinMeshCommand workstation-01 { param($p) Test-Path $p } -ArgumentList 'C:\Windows'
Test-WinMeshFleet          # проверить все хосты из конфига сразу
```

## Примеры использования

Всё ниже предполагает, что хост `workstation-01` настроен (шаги 1–5).

**Выполнить команду и прочитать результат.** `Invoke-WinMeshCommand` возвращает настоящие объекты, а не текст — передавайте их по конвейеру как обычно:

```powershell
Invoke-WinMeshCommand workstation-01 { Get-Service } |
    Where-Object Status -eq 'Running' |
    Measure-Object
```

**Передать аргументы.** Используйте `param()` в блоке и `-ArgumentList`:

```powershell
Invoke-WinMeshCommand workstation-01 {
    param($name, $days)
    Get-EventLog -LogName System -After (Get-Date).AddDays(-$days) -EntryType Error |
        Where-Object Source -like "*$name*"
} -ArgumentList 'disk', 7
```

**Сделать одно и то же на каждой машине парка.** Пройдитесь циклом по конфигу:

```powershell
$cfg = Get-WinMeshConfig
foreach ($name in $cfg.Hosts.Keys) {
    $free = Invoke-WinMeshCommand $name {
        (Get-PSDrive C).Free / 1GB
    }
    "{0,-20} {1,6:N1} GB free on C:" -f $name, $free
}
```

**Запускать скрипт только при здоровом канале.** `Test-WinMeshHost -Quiet` возвращает объект с полем `Ok` и ничего не печатает — удобно для автоматизации:

```powershell
if (-not (Test-WinMeshHost -Name workstation-01 -Quiet).Ok) {
    throw 'workstation-01 is unreachable — aborting'
}
# ... продолжаем, зная, что канал работает
```

**Проверять весь парк в запланированной задаче:**

```powershell
$down = (Test-WinMeshFleet -Quiet) | Where-Object { -not $_.Ok }
if ($down) {
    "$($down.Count) machine(s) down: $($down.Host -join ', ')" | Send-Alert   # ваш уведомитель
}
```

**Копировать файлы на хост или с него.** Для передачи файлов нужна живая сессия; откройте её с сохранёнными учётными данными:

```powershell
$cfg  = Get-WinMeshConfig
$h    = $cfg.Hosts['workstation-01']
$cred = Import-Clixml (Join-Path $cfg.Defaults.CredentialStore "$($h.Credential -replace '[^\w.@-]','_').cred.xml")

$s = New-PSSession -ComputerName $h.Address -Credential $cred
Copy-Item .\report.csv -Destination 'C:\Temp\' -ToSession $s
Copy-Item 'C:\Temp\log.txt' -Destination .\ -FromSession $s
Remove-PSSession $s
```

**Использовать другой файл конфигурации** (например, staging и production):

```powershell
$env:WINMESH_CONFIG = 'C:\fleets\staging.psd1'
Test-WinMeshFleet
# или для отдельного вызова:
Invoke-WinMeshCommand nas-lan { hostname } -Config (Get-WinMeshConfig -Path .\lan.psd1)
```

## SSH вместо WinRM

WinRM используется по умолчанию: он родной для Windows и возвращает объекты. SSH лучше
в двух случаях: машины уже связаны оверлейной VPN со своим SSH-сервером (у NetBird он
есть) либо WinRM вам недоступен — заблокирован политикой или порт закрыт и открыть его
нельзя.

Переключение хоста — одно поле. В ваших скриптах больше ничего не меняется:

```powershell
Hosts = @{
    'workstation-02' = @{
        Address   = 'workstation-02'      # имя в оверлее или IP
        Transport = 'ssh'
        SshUser   = 'Administrator'
    }
}
```

```powershell
Test-WinMeshHost    -Name workstation-02
Invoke-WinMeshCommand workstation-02 { Get-Service } | Where-Object Status -eq 'Running'
```

**Поля `Credential` нет, и шага `Connect-WinMeshHost` нет.** По ssh клиент
аутентифицируется сам — ключом, агентом или, в оверлейной сети, идентичностью пира:
SSH-сервер NetBird аутентифицирует *пира*, поэтому машине, уже входящей в вашу сеть,
ключ вообще не нужен. Шаги 1, 3 и 4 настройки (bootstrap, учётные данные, `Connect-WinMeshHost`) к ней просто не относятся.

Объекты вы по-прежнему получаете, а не текст. Scriptblock и его аргументы упаковываются
в base64 и передаются через `powershell -EncodedCommand` (`pwsh` на Linux/macOS), а результат сериализуется на
удалённой стороне тем же движком CliXml, что использует remoting, и здесь восстанавливается.

**Опции SSH** — для хоста или в `Defaults`:

| Ключ | По умолчанию | Значение |
|---|---|---|
| `SshUser` | *(пусто)* | удалённая учётная запись; пусто — пусть решает `ssh` |
| `SshPort` | `22` | |
| `SshShell` | `powershell` | `powershell` (5.1, в Windows есть всегда) или `pwsh`; Linux/macOS-целям нужен `pwsh` или полный путь к нему |
| `SshTimeout` | `15` | секунды, превращается в `ConnectTimeout` |
| `SshOptions` | `@()` | дополнительные опции `-o`, например `@('StrictHostKeyChecking=accept-new')` |

Всё более специфичное — jump-хосты, ключи для отдельных хостов, алиасы — относится в
ваш `~/.ssh/config`, который `ssh` читает как обычно. winmesh это не дублирует.


### Что передаётся по каналу

Для тех, кому нужны внутренности (`functions/Invoke-WinMeshSsh.ps1`). Один вызов выполняет примерно следующее:

```text
ssh -o BatchMode=yes -o ConnectTimeout=<SshTimeout> [-p <SshPort>] [-o <каждый элемент SshOptions>] [user@]<Address> \
    "<SshShell> -NoProfile -NonInteractive -EncodedCommand <base64 нагрузки в UTF-16LE>"
```

- **Без запросов.** `BatchMode=yes` означает, что `ssh` никогда не спрашивает пароль или парольную фразу. Аутентификация должна работать без участия человека: ключ, агент или идентичность пира оверлейной сети. `-p` добавляется, только если порт не 22.
- **Нагрузка** — небольшой скрипт PowerShell: он декодирует ваши аргументы (сериализованные через `PSSerializer`, затем base64) и текст вашего scriptblock (base64), выполняет блок, сериализует результат через `PSSerializer` и печатает его одной строкой-маркером: `@@WINMESH-OK@@<base64>`. Сбой внутри блока вместо этого печатает `@@WINMESH-ERR@@<base64>`.
- **Результаты.** Строка-маркер десериализуется локально, поэтому вы получаете объекты. Как и при удалённом взаимодействии, они восстановлены из сериализованных данных (наборы свойств), а не являются живыми объектами. Аргументы должны сериализоваться тем же способом.
- **Всё остальное, что печатает удалённая сторона** (`Write-Host`, вывод нативных команд), передаётся в ваш хост, а не проглатывается.
- **Ошибки.** Сбой внутри блока пробрасывается локально как `winmesh(ssh) <address>: <message>` — по каналу идёт только текст сообщения, а не объект ошибки. Если строка-маркер не вернулась вовсе, ошибка выглядит как `winmesh(ssh) <address>: no response from the target — <вывод ssh или код выхода>`; для кода выхода 127 (`sh`/`bash`/`zsh`) или 9009 (`cmd.exe`), либо если в выводе сказано, что команда не найдена, добавляется подсказка задать `SshShell`.
- **Нагрузка не секретна.** Это обычный аргумент командной строки; base64 — кодировка, а не защита. Не кладите секреты в scriptblock или `-ArgumentList` — они могут попасть в списки процессов и в вывод `-Verbose`, который печатает полный список аргументов `ssh`. Весь скрипт передаётся в командной строке, поэтому очень большой scriptblock может упереться в ограничения на длину командной строки (не измерялось).
- **Проверка порта**, которую использует `Test-WinMeshHost`, открывает обычное TCP-соединение (а не `Test-NetConnection`, который есть только в Windows) и читает SSH-баннер.

### Если вы используете оверлейную VPN

`AllowedSubnets` (применяется bootstrap-скриптом WinRM) действует только на WinRM. Если
вы обслуживаете SSH через Windows OpenSSH, а не через собственный сервер VPN, сузьте
порт 22 самостоятельно:

```powershell
Set-NetFirewallRule -Name 'OpenSSH-Server-In-TCP' -RemoteAddress '100.64.0.0/10'
```

## Выбор разрешённых подсетей

Bootstrap сужает порт WinRM до `Defaults.AllowedSubnets` из вашего конфига. Выберите значение, соответствующее тому, как связаны ваши машины:

| Сеть | AllowedSubnets |
|---|---|
| Tailscale / NetBird | `@('100.64.0.0/10')` — диапазон CGNAT (по умолчанию) |
| ZeroTier | подсеть вашей сети, например `@('10.147.17.0/24')` |
| Обычная LAN | например `@('192.168.1.0/24')` |
| Несколько сразу | `@('192.168.1.0/24','100.64.0.0/10')` |
| Не сужать (доверенная LAN) | `@()` |

Можно также передать значение напрямую, игнорируя умолчание из конфига:

```powershell
New-WinMeshBootstrap -AllowedSubnets '192.168.1.0/24' -OutFile .\bootstrap-lan.ps1
```

## Просмотр и изменение того, каким сетям разрешено подключаться

`AllowedSubnets` — единственное место, которое решает, каким исходным сетям разрешён
доступ к порту WinRM хоста. Оно применяется при bootstrap; посмотреть или применить
его заново позже можно, не вспоминая команды файрвола:

```powershell
Get-WinMeshFirewallScope -Name workstation-01            # текущая область + совпадает ли она с конфигом
Set-WinMeshFirewallScope -Name workstation-01 -WhatIf    # предпросмотр
Set-WinMeshFirewallScope -Name workstation-01            # применить AllowedSubnets из конфига
```

`Set-WinMeshFirewallScope` откажется работать, если сужение отрежет вашу собственную
живую сессию (ни один подключённый источник не попадает в новые диапазоны) — передавайте
`-Force` только сидя за консолью. Хост может переопределить глобальное значение своим
`AllowedSubnets` (например, машина, доступная через другой оверлей):

```powershell
Hosts = @{
    'nas-zt' = @{
        Address        = '10.147.17.20'
        Credential     = 'admin@nas-zt'
        AllowedSubnets = @('10.147.17.0/24')   # только для этого хоста; переопределяет Defaults
    }
}
```

## Подключение из другой сети

Для доступа к хосту должны выполняться оба условия: источник должен уметь
*маршрутизироваться* до машины, а его адрес — попадать в `AllowedSubnets`.

- **Вы физически в другом месте (офис, отель, дом).** Менять ничего не нужно —
  Tailscale/NetBird работает поверх любого доступного интернета, вы остаётесь в
  оверлее, и хост достижим по своему оверлейному адресу. Обычный случай.
- **Добавить ещё один оверлей (например, ZeroTier).** Подключите к нему обе машины,
  добавьте его подсеть в `AllowedSubnets` (ZeroTier не входит в диапазон CGNAT
  `100.64.0.0/10`), выполните `Set-WinMeshFirewallScope` и добавьте новый адрес хоста
  в `TrustedHosts` на контроллере.
- **Конкретная доверенная LAN без оверлея.** Добавьте эту подсеть — как можно уже
  (`/24` или один `/32`), помня, что после этого любой в ней сможет достучаться до WinRM.

## Заметки по безопасности

- **Границей лучше считать членство в оверлее.** Чтобы достучаться до хоста, нужно быть
  в его оверлее, а для этого нужна ваша аутентификация в Tailscale/NetBird. Диапазон
  файрвола — второй слой, отсекающий физическую LAN и публичные адреса.
- **Не открывайте WinRM для всей корпоративной или публичной подсети.** Вместо этого
  заходите на хост через оверлей из той сети; оверлей туннелируется через любой интернет.
- **`AllowedSubnets` заменяет, а не дополняет.** Перечисляйте сразу все нужные сети;
  пустой список (`@()`) означает «не сужать» (`Any`) — только для доверенной LAN.
- **WinRM 5985 шифруется Negotiate/Kerberos**, это не открытый текст, но всё равно
  админ-канал — держите исходный диапазон настолько узким, насколько позволяет настройка.
- **Профиль правила по-прежнему важен.** Оно применяется к Domain+Private; если
  оверлейный адаптер отнесён к Public, правило его не покроет. Держите оверлейные
  адаптеры Private либо расширьте профиль правила после того, как задан исходный диапазон.

| Команда | Что делает | Где выполняется | Админ |
|---|---|---|---|
| `Get-WinMeshConfig` | загрузить и проверить конфиг | контроллер | нет |
| `Register-WinMeshCredential` | сохранить учётные данные цели (DPAPI) — *только winrm, Windows-контроллер* | контроллер | нет |
| `Connect-WinMeshHost` | настроить клиент: WinRM + TrustedHosts — *только winrm, Windows-контроллер* | контроллер | **да** |
| `Test-WinMeshHost` / `Test-WinMeshFleet` | проверить канал | контроллер | нет |
| `Invoke-WinMeshCommand` | выполнить команду на хосте | контроллер | нет |
| `New-WinMeshBootstrap` | сгенерировать скрипт подготовки цели | контроллер | нет |
| `Get-WinMeshFirewallScope` / `Set-WinMeshFirewallScope` | показать / заново применить, каким сетям разрешён доступ к WinRM — *только winrm* | контроллер (действует на цели через WinRM) | нет на контроллере; учётная запись на цели должна иметь право менять правила файрвола |
| *(bootstrap на цели)* | включить WinRM, сузить порт — *только winrm* | **цель** | **да** |

Параметры — как они определены в коде (`functions/`):

| Команда | Параметры |
|---|---|
| `Get-WinMeshConfig` | `-Path` (по умолчанию: `$env:WINMESH_CONFIG`, иначе `config/hosts.psd1` рядом с модулем) |
| `Invoke-WinMeshCommand` | `-Name` (позиция 0), `-ScriptBlock` (позиция 1), `-ArgumentList`, `-Config` (объект конфига из `Get-WinMeshConfig`) |
| `Test-WinMeshHost` | `-Name` (позиция 0), `-Config`, `-Quiet` |
| `Test-WinMeshFleet` | `-Config`, `-Quiet` |
| `New-WinMeshBootstrap` | `-AllowedSubnets`, `-OutFile`, а также `-Name` (принимается как метка, но сгенерированный скрипт не меняет) |
| `Register-WinMeshCredential` | `-Id` (обязателен), `-Credential`, `-Store` |
| `Connect-WinMeshHost` | `-Name` (обязателен), `-Config`, `-WhatIf` |
| `Get-WinMeshFirewallScope` | `-Name` (позиция 0), `-Config` |
| `Set-WinMeshFirewallScope` | `-Name` (позиция 0), `-Config`, `-Force`, `-WhatIf` |

### Test-WinMeshHost подробно

`Test-WinMeshHost` проверяет всю цепочку, выводит читаемый отчёт (если не указан `-Quiet`) и всегда возвращает объект: `Host`, `Address`, `Transport`, `Ok` (истина, только если прошли все проверки) и `Checks` (список элементов `Check`, `Ok`, `Detail`). Какие проверки выполняются, зависит от транспорта хоста:

| Транспорт | Проверки (по порядку) |
|---|---|
| `winrm` (Windows-контроллер) | `WinRM port 5985` · `WS-Management responds` · `credentials` · `command runs` · `full admin token` (две последние — только если прошли проверки учётных данных и WS-Management) |
| `ssh` | `ssh port <n>` с баннером сервера в деталях · `command runs` (показывает хост, пользователя и ОС) · `full admin token` — только для Windows-цели |
| `winrm`-хост на Linux/macOS-контроллере | одна проваленная проверка `WinRM client` — хост попадает в отчёт, а не вызывает исключение, поэтому смешанный парк всё равно проверяется |

На SSH-цели под Linux или macOS проверки админ-токена нет: обычный вход — это нормально, root получают через `sudo`, а в детали *command runs* пишется `root` или `not root`. Статус `reduced` у админ-токена на Windows-хосте означает, что сессия не несёт полный токен администратора (WinRM: bootstrap выставляет `LocalAccountTokenFilterPolicy`; SSH: некоторые серверы, включая тот, что поставляет NetBird, выдают неповышенную сессию).

`Test-WinMeshFleet` запускает `Test-WinMeshHost` для каждого хоста из конфига по очереди, печатает сводку и возвращает список объектов результата. Это функция, поэтому код возврата процесса она не выставляет — используйте поле `Ok`.

### Хранилище учётных данных

- **Что сохраняется.** `Register-WinMeshCredential -Id <id>` записывает `<id>.cred.xml` (символы вне `[\w.@-]` заменяются на `_`) в хранилище учётных данных — по умолчанию `~\.winmesh\creds` — через `Export-Clixml`. В Windows пароль в этом файле зашифрован DPAPI: прочитать его может только тот же аккаунт на той же машине.
- **Какой логин указывать.** Доменная машина: `DOMAIN\user`; машина в рабочей группе: `COMPUTERNAME\user` — bootstrap печатает точную строку как `LoginForCred`.
- **Запрос данных.** Без `-Credential` спрашивает через `Get-Credential` и, если окно не появилось, переходит на ввод в консоли.
- **Где используется.** `Invoke-WinMeshCommand`, `Test-WinMeshHost` и команды области файрвола читают файл по id `Credential` хоста. Если файла нет, выдаётся `No credential '<id>'. Create it: Register-WinMeshCredential -Id '<id>'`.
- **Только Windows.** Вне Windows `Export-Clixml` записал бы пароль простым hex, поэтому `Register-WinMeshCredential` там отказывается работать. SSH-путь это хранилище не использует.

### Bootstrap-скрипт

`New-WinMeshBootstrap` возвращает скрипт (а с `-OutFile` сохраняет его в UTF-8 с BOM) из четырёх пронумерованных шагов:

1. `Enable-PSRemoting -Force -SkipNetworkProfileCheck` (оверлейный адаптер часто находится в профиле Public, из-за чего обычный `Enable-PSRemoting` отказывается работать).
2. Выставляет `RemoteAddress` у каждого включённого входящего правила файрвола с локальным портом 5985 в разрешённые подсети. Пустой список пропускает сужение; если правило для 5985 не найдено, выводится предупреждение проверить вручную.
3. Выставляет `LocalAccountTokenFilterPolicy = 1` в `HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`, чтобы локальные учётки получали полный токен администратора в удалённых сессиях (нужно для машин вне домена и для администраторов, отличных от встроенного).
4. Выводит факты о машине для конфига: `ComputerName`, `Domain`, `InDomain`, `User`, `LoginForCred`.

Приоритет подсетей: `-AllowedSubnets`, если указан; иначе `Defaults.AllowedSubnets` из конфига; иначе — только если конфиг не удаётся загрузить — `100.64.0.0/10`.

### Что меняется на ваших машинах

| Где | Что меняется | Кто меняет |
|---|---|---|
| Контроллер | служба WinRM запущена и переведена в Automatic; адрес цели добавлен в `TrustedHosts` | `Connect-WinMeshHost` (поддерживает `-WhatIf`) |
| Контроллер | `<id>.cred.xml` в хранилище учётных данных | `Register-WinMeshCredential` |
| Цель (WinRM) | включён PowerShell Remoting; сужен `RemoteAddress` входящих правил 5985; `LocalAccountTokenFilterPolicy = 1` (удалённые сессии локальных учёток получают полный админ-токен) | сгенерированный bootstrap-скрипт |
| Цель (WinRM) | те же правила файрвола, позже заново с другой областью | `Set-WinMeshFirewallScope` |
| Цель (SSH, необязательно) | установлен и запущен OpenSSH, правило `winmesh-sshd` для TCP/22 (Windows) или ограниченные правила UFW/firewalld (Linux), более широкие разрешения TCP/22 отключены или удалены | скрипты из `scripts/` — см. [установку SSH-сервера](docs/ssh-server-setup.md) |

## Справочник по конфигу

`config/hosts.psd1` — файл данных PowerShell (`.psd1`, а не YAML: в Windows PowerShell 5.1 нет встроенного YAML-парсера, а `.psd1` разбирается безопасно, без выполнения кода). `config/hosts.example.psd1` — шаблон с комментариями; ваш настоящий `config/hosts.psd1` исключён из git.

```powershell
@{
    Defaults = @{
        Transport       = 'winrm'                  # 'winrm' or 'ssh'
        CredentialStore = '~\.winmesh\creds'       # where encrypted credentials live
        AllowedSubnets  = @('100.64.0.0/10')       # subnets allowed to reach WinRM
    }
    Hosts = @{
        'workstation-01' = @{
            Address    = '100.100.10.11'
            Credential = 'admin@workstation-01'
            Note       = 'optional free-text note'
        }
        'workstation-02' = @{
            Address    = 'workstation-02'          # same fleet, ssh instead of WinRM
            Transport  = 'ssh'
            SshUser    = 'Administrator'           # no Credential: see "Over SSH instead of WinRM"
        }
    }
}
```

Указать winmesh другой конфиг можно через `$env:WINMESH_CONFIG` или параметры `-Config`/`-Path`.

**Ключи.** Ключ в `Defaults` действует для всех хостов; тот же ключ у хоста переопределяет его, кроме `CredentialStore`, который читается только из `Defaults`.

| Ключ | Где | По умолчанию | Значение |
|---|---|---|---|
| `Address` | хост | *(обязателен)* | адрес в оверлее/LAN или DNS-имя |
| `Transport` | умолчания, хост | `winrm` | `winrm` или `ssh`; всё остальное отвергается |
| `Credential` | хост | — | id сохранённых учётных данных; **обязателен для `winrm`**, для `ssh` не используется |
| `Note` | хост | — | свободный текст для вас; winmesh его не читает |
| `CredentialStore` | умолчания | `~\.winmesh\creds` | каталог учётных данных; `~` раскрывается в домашний каталог, а `\` или `/` работают на любой ОС |
| `AllowedSubnets` | умолчания, хост | `@('100.64.0.0/10')` | исходные сети для порта WinRM; `@()` означает «не сужать» ([подробнее](#выбор-разрешённых-подсетей)) |
| `SshUser`, `SshPort`, `SshShell`, `SshTimeout`, `SshOptions` | умолчания, хост | см. [опции SSH](#ssh-вместо-winrm) | только для ssh-транспорта |

**Проверка.** `Get-WinMeshConfig` завершается ошибкой с сообщением, если файла нет, если `Hosts` пуст, если у хоста нет `Address`, если транспорт не `winrm` и не `ssh`, или если у `winrm`-хоста нет `Credential`. Устаревшее значение по умолчанию `TailscaleCidr` используется как `AllowedSubnets`, когда сам `AllowedSubnets` не задан. Команда возвращает объект с полями `Path`, `Defaults` (объединённые со встроенными умолчаниями) и `Hosts`; остальные команды принимают его через `-Config`.

## Чего он намеренно не делает

- **Не обходит первый админ-шаг на цели.** В принципе невозможно; модуль лишь генерирует скрипт.
- **Не переносит учётные данные между контроллерами.** Файл DPAPI расшифровывается только там, где создан. Хранилище локально намеренно.
- **Не управляет SSH-ключами и паролями.** По ssh аутентификация — это то, о чём договорится ваш `ssh`-клиент: ключ, агент или идентичность пира оверлейной сети. winmesh для ssh-пути никогда не запрашивает, не хранит и не пересылает секреты.
- **Модуль не устанавливает SSH-сервер.** В отличие от WinRM, bootstrap для него нет: либо оверлейная VPN уже предоставляет сервер (NetBird), либо вы один раз ставите OpenSSH-сервер (а на Linux/macOS-цель — ещё и PowerShell 7). Для этого шага есть необязательные отдельные скрипты для Windows и Linux — см. [установку SSH-сервера](docs/ssh-server-setup.md) (на английском).

## Встроенные грабли

Собрано из реальной отладки — каждая стоила времени:

- **`Set-Item WSMan:...` винит удалённый хост, когда на самом деле проблема в локальной службе WinRM.** Если она остановлена, обращение к диску `WSMan:` падает с ошибкой о недоступности цели. `Connect-WinMeshHost` сначала запускает службу.
- **`Enable-PSRemoting` открывает порт с `RemoteAddress=Any`.** Сужение до доверенных подсетей — обязательный шаг, встроенный в bootstrap. Пропустите его — и порт окажется открыт шире, чем вы думаете.
- **TrustedHosts нужен даже в домене** при подключении по IP: Kerberos не применяется, и аутентификация откатывается на NTLM.
- **Скрипты — UTF-8 с BOM.** Без BOM Windows PowerShell 5.1 читает не-ASCII как ANSI и не может разобрать файл.

Именно про SSH:

- **`-EncodedCommand` ждёт base64 от UTF-16LE, а не UTF-8.** Закодируйте нагрузку как UTF-8 — и PowerShell либо прочитает мусор, либо откажется разбирать. Поэтому транспорт кодирует через `[Text.Encoding]::Unicode`.
- **Нельзя вручную заквотировать команду для удалённой оболочки.** Windows OpenSSH по умолчанию запускает `cmd.exe`, а PowerShell — если изменён `DefaultShell`, и они по-разному трактуют кавычки. Один base64-токен вообще снимает вопрос, и одна и та же строка работает в любой оболочке.
- **`ConvertTo-CliXml` не существует в Windows PowerShell 5.1.** Используйте `[System.Management.Automation.PSSerializer]::Serialize()` / `::Deserialize()`, которые есть и в 5.1, и в 7.
- **В оверлейной сети порт 22 может отвечать не тот сервер, что вы настроили.** NetBird поставляет собственный SSH-сервер и занимает порт на оверлейном адресе, так что настроенная вами служба Windows OpenSSH может простаивать. `Test-WinMeshHost` печатает SSH-баннер именно поэтому — читайте его.
- **Сессия, открытая SSH-сервером оверлея, может не нести полный админ-токен,** даже для учётки администратора. `Test-WinMeshHost` сообщает об этом отдельной проверкой, а не даёт проявиться позже запутанным access-denied.

На **неанглийской Windows** или на доменной машине с недоступным DC:

- **`IsInRole('Administrators')` ненадёжен на локализованной Windows — может
  бросить исключение или вернуть неверное `$false`.** Встроенная группа может быть
  локализована (`BUILTIN\Администраторы` на русской установке), а строковая перегрузка
  разрешает по *имени*. Измерено в обе стороны: на русской установке с локализованной
  группой английский литерал вызвал `MethodInvocationException`; на другой машине
  неразрешимое имя просто вернуло `$false` (и в 5.1, и в 7). Локализованное имя,
  перечисление `[WindowsBuiltInRole]::Administrator` и сырой SID вернули верный ответ.
  В любом случае исправный канал отображается как `command runs: False` — исключение
  роняет весь вызов изнутри удалённого scriptblock, а неверное `$false` просто неверно.
  Всегда используйте перечисление или `S-1-5-32-544`, но не английское имя.
- **`icacls` и `Add-LocalGroupMember` ломаются так же, но по другой причине.**
  Передача имени `"Administrators"` заставляет Windows его разрешать, а на доменной
  машине этот запрос уходит на контроллер домена — так что при недоступном DC вы
  получаете *«could not establish trust relationship with the primary domain»* при
  совершенно локальной операции. Известным SID поиск не нужен:
  `icacls f /grant "*S-1-5-32-544:F" /grant "*S-1-5-18:F"` и
  `Add-LocalGroupMember -Group (Get-LocalGroup -SID S-1-5-32-544)`.
- **Доменная учётка может пройти publickey-аутентификацию и всё равно не открыть сессию.**
  В логе OpenSSH видно `Accepted publickey for <user>`, затем клиент получает
  `Connection reset by peer` — и **дальше ничего не логируется**, потому что сбой
  происходит за пределами логирования sshd. Вход по ключу строит токен пользователя
  через S4U, а для доменной учётки это требует живого DC; ваша интерактивная сессия
  работает лишь потому, что использует кэшированные учётные данные, недоступные sshd.
  Исправление — не в настройке sshd: используйте **локальную** учётную запись. На
  доменной машине `Get-LocalGroupMember -SID S-1-5-32-544` обычно показывает такую.
- **Вставка ключа в консоль может его разорвать, а sshd вам об этом не скажет.**
  Длинная строка `$key = 'ssh-ed25519 …'` переносится по ширине консоли, перевод
  строки оказывается *внутри* строки, и `authorized_keys` получает два фрагмента.
  Некорректные строки молча пропускаются, так что симптом — обычный
  `Permission denied` при выглядящем корректно файле. Проверяйте длинами, а не на глаз —
  валидная строка ed25519 — это одна строка примерно в 110 символов:
  `Get-Content $f | ForEach-Object { $_.Length }`.
- **Админские ключи лежат совсем в другом месте.** Для любой учётки из группы
  администраторов стандартный `sshd_config` содержит
  `Match Group administrators` → `__PROGRAMDATA__/ssh/administrators_authorized_keys`.
  Ключ, положенный в `C:\Users\<name>\.ssh\authorized_keys`, игнорируется — как и
  этот общий файл, если его ACL шире, чем SYSTEM + Administrators.
- **Правило, стоящее за первыми двумя: на локализованной Windows всё, что
  разрешается или форматируется через системную локаль, — ошибка переносимости.**
  За час на одной машине нашлись два примера — `IsInRole('Administrators')`,
  бросающий исключение, и отдельный CLI, у которого `toLocaleString()` печатал `1 401`
  там, где `en-US` печатает `1,401`, ломая собственный разбор вывода. Оба выглядят
  корректно на английской машине, и ни один не ловится прогоном тестов под Linux.
  Фиксируйте локаль (`toLocaleString('en-US')`) и обращайтесь к принципалам по SID.

### Linux и macOS

- **`$IsWindows` не существует в Windows PowerShell 5.1.** Там он равен `$null`,
  и `if ($IsWindows)` молча считает любую машину с 5.1 не-Windows. Scriptblock,
  который может выполниться на цели с 5.1, проверяет `$env:OS -eq 'Windows_NT'`.
- **`WindowsIdentity` вне Windows бросает исключение.** Проверка админа, работающая
  на любой Windows-цели, на Linux/macOS даёт `PlatformNotSupportedException`; там
  вопрос решает `id -u` — и «не root» это норма, а не сбой.
- **Обратный слэш в Linux/macOS — обычный символ имени файла.** `Join-Path $dir 'config\hosts.psd1'`
  даёт один файл с именем `config\hosts.psd1`. Соединяйте сегменты по отдельности.
- **Вне Windows `Export-Clixml` не шифрует учётные данные.** Пароль хранится как
  hex от UTF-16 — его прочитает любой, кто может прочитать файл. Поэтому хранилище
  учётных данных (а с ним и WinRM) — только для Windows.

### Управление целью из скрипта

- **Не встраивайте не-ASCII литералы в передаваемый скрипт.** `.ps1` с кириллицей
  после `scp` оказался испорчен, и PowerShell 5.1 не смог его разобрать — это тот же
  случай с BOM, пришедший другим путём. Получайте локализованную строку во время
  выполнения — тогда литерал вообще не нужен:
  `([Security.Principal.SecurityIdentifier]'S-1-5-32-544').Translate([Security.Principal.NTAccount]).Value`.
- **Не квотируйте вручную и разовую команду.** Транспорт избегает этого упаковкой в
  base64 (см. выше), но в консоли та же ловушка срабатывает: разовая
  `powershell -Command "... try { } catch { } ..."` через `ssh` потеряла фигурные
  скобки на двух слоях квотирования и упала с `MissingCatchOrFinally`. Запишите файл и
  запустите `powershell -File` — ровно так, как фактически делает транспорт.
- **Большая загрузка, запущенная *на* цели, может не удаться там, где отправка с
  контроллера проходит.** `Invoke-WebRequest` прервался с `IOException` на середине
  файла в 100 МБ, а возобновление через `curl.exe -C -` не смогло даже открыть
  частичный файл в каталоге, доказанно доступном для записи за минуты до этого. `scp`
  тех же байтов с контроллера сработал с первого раза. Причина не установлена —
  защитное ПО очевидный подозреваемый, но это не подтверждено. Полезно знать как
  обходной путь, а не как объяснение.

## Требования

Windows PowerShell 5.1 или PowerShell 7 в Windows; PowerShell 7 в Linux и macOS (см. [Платформы](#платформы)). Сеть, дающая машинам стабильные, взаимно достижимые адреса — оверлей (Tailscale, NetBird, ZeroTier) или обычная LAN. Права администратора нужны только для `Connect-WinMeshHost` на контроллере и bootstrap на каждой цели — к ssh-хостам ни то ни другое не относится. Для ssh-транспорта нужны `ssh`-клиент на контроллере (встроен в Windows 10/11, Server 2019+, Linux и macOS) и SSH-сервер на цели — а если цель на Linux или macOS, то и PowerShell 7 на ней.

Для повторяемой установки OpenSSH на цель под Windows (Win32-OpenSSH) и Linux см. [установку SSH-сервера](docs/ssh-server-setup.md). Скрипты требуют явно указать разрешённую подсеть-источник и не открывают TCP/22 для всех адресов.

## Диагностика

Сообщения ниже выдаёт сам модуль или о них сообщает `Test-WinMeshHost`.

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `Config not found: <path>` | нет `config/hosts.psd1`, либо `$env:WINMESH_CONFIG` указывает на другой файл | скопируйте `config/hosts.example.psd1` в `config/hosts.psd1` и заполните |
| `Host '<name>' is not in config <path>` | имени нет среди ключей `Hosts`, либо загружен другой конфиг | проверьте ключ и `$env:WINMESH_CONFIG` |
| `Host '<name>': Credential is missing` | у `winrm`-хоста нет id `Credential` | добавьте id или задайте `Transport = 'ssh'` |
| `No credential '<id>'. Create it: Register-WinMeshCredential ...` | на этом контроллере нет файла учётных данных (файлы DPAPI не переносятся) | выполните здесь `Register-WinMeshCredential -Id '<id>'` |
| `... needs a Windows controller ...` | `winrm`-хост используется с Linux/macOS-контроллера | задайте для хоста `Transport = 'ssh'` |
| `WinRM port 5985` не проходит, `no connection` | не запускался bootstrap, либо адрес контроллера вне `AllowedSubnets`, либо машины не маршрутизируются друг к другу | запустите bootstrap; проверьте область; проверьте сеть (оверлей подключён, одна LAN) |
| `WS-Management responds` не проходит при открытом порте | в `TrustedHosts` нет адреса, либо WinRM на цели не настроен | выполните `Connect-WinMeshHost -Name <имя>` (админ) и bootstrap |
| `full admin token` — reduced | у сессии нет полного токена администратора | WinRM: убедитесь, что bootstrap выполнялся (`LocalAccountTokenFilterPolicy`); SSH: некоторые серверы, включая NetBird, выдают неповышенную сессию |
| `winmesh(ssh) <address>: no response from the target — ... PowerShell was not found on the target` | неверный `SshShell` для цели | `pwsh` на Linux/macOS либо полный путь из `command -v pwsh` на цели |
| `winmesh(ssh) ...` с `Permission denied` или таймаут | вход по ключу или через агент не работает без участия человека (`BatchMode=yes`) | сначала добейтесь, чтобы обычный `ssh` входил без запросов; про ловушки с файлами ключей см. [Грабли](#встроенные-грабли) |
| `Connection reset by peer` сразу после того, как журнал пишет `Accepted publickey` | доменная учётная запись на доменной цели без доступного DC | используйте локальную учётную запись — см. [Грабли](#встроенные-грабли) |
| баннер проверки `ssh port` — не тот сервер, который вы установили | на порту 22 отвечает собственный SSH-сервер оверлея | прочитайте баннер в проверке — см. [Грабли](#встроенные-грабли) |
| `Set-WinMeshFirewallScope`: `Refusing: no live WinRM source falls inside the new ranges` | применение отрезало бы вашу собственную сессию | добавьте свою подсеть-источник в `AllowedSubnets`; `-Force` — только на консоли |
| `Get-WinMeshFirewallScope` сообщает `InSync = False` | действующее правило отличается от `AllowedSubnets` в конфиге | выполните `Set-WinMeshFirewallScope -Name <имя> -WhatIf`, затем без `-WhatIf` |
| скрипт не разбирается в Windows PowerShell 5.1 | файл сохранён без BOM | сохраните в UTF-8 с BOM |

## Статус и известные ограничения

winmesh — версия 0.2.1. Это небольшой модуль, который задуман так, чтобы его можно было прочитать за один присест, и без зависимостей; ставится он клонированием репозитория и импортом манифеста (других способов установки в репозитории не описано).

- **Автоматического набора тестов нет.** `CONTRIBUTING.md` описывает ручные проверки: разбор каждого `.ps1`/`.psd1`, `Test-ModuleManifest`, поведение под `-WhatIf`, дымовой тест на реальном хосте и способ проверить ssh-обмен без второй машины, подменив `ssh` функцией.
- **WinRM — только HTTP на порту 5985.** Обработки HTTPS (5986) в модуле нет. Канал шифруется Negotiate/Kerberos, но это всё равно админ-канал.
- **WinRM требует Windows на обоих концах.** На Linux/macOS-контроллере команды WinRM отказываются работать с понятным сообщением, а проверки состояния сообщают о проваленной проверке `WinRM client`.
- **Последовательно.** `Test-WinMeshFleet` проверяет хосты один за другим, а `Invoke-WinMeshCommand` обращается к одному хосту за вызов; чтобы выполнить что-то на всех хостах, пройдите по конфигу циклом сами ([пример](#примеры-использования)).
- **Результаты — десериализованные объекты** в обоих транспортах (данные, а не живые объекты).
- **SSH не интерактивен** (`BatchMode=yes`) и не управляет ключами, паролями и политикой ключей хостов; для этого есть `SshOptions` и `~/.ssh/config`.
- **Защита области файрвола — только IPv4.** Проверка самоблокировки сравнивает живые источники WinRM с новыми диапазонами как IPv4 CIDR, а `Get-WinMeshFirewallScope` сравнивает области по префиксу сети — это лёгкая проверка, а не точное сравнение.
- **Затрагиваются все включённые входящие правила с локальным портом 5985** — на цели.
- **Установщики SSH-сервера** поддерживают `apt`, `dnf`, `yum` и `pacman` на Linux и работают только с UFW или firewalld; они не создают учётные записи и не добавляют публичные ключи.
- **Измеренные утверждения.** Наблюдения про локализованную Windows и про загрузку в [Граблях](#встроенные-грабли) приведены так, как они наблюдались; причина сбоя при загрузке большого файла не установлена.
