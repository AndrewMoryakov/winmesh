# Плейбук: создание и фиксация подключения (для агентов)

Генерик-процедура. Конкретные хосты сюда **не** пишем — они идут в приватный
`connections.local.md`. Задача плейбука: провести через настройку без известных
ловушек и заставить записать результат так, чтобы следующий вошёл одной командой.

`connections.local.md` — общая записная книжка про **все** машины, к которым
подключаешься с этой машины, а не только про хосты winmesh. Плейбук годится для
любого такого подключения.

---

## Шаг 1. Установить факты о цели (не предполагать)

Прежде чем что-то чинить, установи и **проверь**:

- **Настоящий адрес.** В оверлей-сетях (NetBird/Tailscale) имя пира ≠ идентичность
  машины: пир может быть переименован, переехать на новый IP или указывать на
  чужую ОС. Бери адрес из самоотчёта машины (`netbird status` **на ней**), а не
  из чужого конфига.
- **ОС и SSH-сервер — по баннеру.** `ssh -vv user@host true 2>&1 | grep 'remote software'`.
  `OpenSSH_for_Windows` против `OpenSSH ... Ubuntu` мгновенно ловит «не ту машину»
  ещё до всякой авторизации.
- **Достижимость и порт.** `nc -vz host 22` (Linux) / `Test-NetConnection host -Port 22` (Win).

## Шаг 2. Выбрать транспорт и учётку

- **SSH** — предпочтительно. Аутентификация по ключу; на сервере обычно
  `passwordauthentication no`, поэтому пароль не поможет — нужен ключ.
- **WinRM** — только когда Windows **с обеих сторон**: и цель, и машина, с
  которой подключаешься. С Linux/macOS winmesh ходит только по SSH. Учётка —
  локальная (`COMPUTERNAME\user`) или доменная (`DOMAIN\user`), в том виде, как
  её печатает bootstrap (README, шаг 3). **Не** учётная запись Microsoft
  (`*@outlook.com`, `*@hotmail.com`): она не проходит сетевой NTLM-вход, её
  облачный пароль для WinRM бесполезен. Для такой машины заводи локального
  пользователя.
- Приватный ключ живёт на **клиенте** (кто инициирует коннект) и никогда его не
  покидает; на сервер идёт только публичная половина.

## Шаг 3. Настроить (по типу цели)

**Linux-сервер:** добавить публичный ключ клиента в `~/.ssh/authorized_keys`
нужного пользователя (одной строкой, не трогая остальные), `chmod 600`.

**Windows-цель:** список типовых ловушек — в разделе ниже. Кратко:
- нужен **повышенный** PowerShell (быть админом мало — UAC даёт урезанный токен);
- ключ **админа** читается только из
  `C:\ProgramData\ssh\administrators_authorized_keys` с ACL только
  `Administrators`+`SYSTEM`; личный `~/.ssh/authorized_keys` для админа
  игнорируется;
- если есть физический/RDP-доступ — настраивай **локально**, это обнуляет все
  трудности удалённой аутентификации.

**SSH-сервера на цели нет:** поставь его скриптом winmesh —
`scripts/windows/Install-Win32OpenSSH.ps1` или
`scripts/linux/install-openssh-server.sh`, подробности в
[docs/ssh-server-setup.md](ssh-server-setup.md). Сначала проверь по тому
документу, не стоит ли сервер уже. Скрипты закрывают TCP/22 для всех адресов вне
переданных диапазонов (Linux-скрипт — только при активном UFW или firewalld):
включи в них сеть, с которой подключаешься сам, и держи консоль/RDP открытой до
первого успешного входа. Чтобы winmesh выполнял команды на Linux-цели, там
нужен ещё `pwsh`.

## Шаг 4. Проверить именно тот путь, которым будут пользоваться

Не «просто пингануть», а войти той же учёткой и тем же ключом, что пойдут в
реальную работу. Права приватного ключа OpenSSH проверяет **относительно
запускающего пользователя** — тестируй под той же учёткой, иначе получишь ложный
отказ.

## Шаг 5. ⚑ Зафиксировать в `connections.local.md`

Обязательный шаг для любого подключения, не только к хостам winmesh. Допиши
запись по шаблону:

```markdown
## <короткое-имя>

- Статус: проверено <ГГГГ-ММ-ДД>, <чем именно проверено>.
- Назначение / что за машина: <одна строка>.
- Адрес: `<IP или имя>`  (источник истины: <напр. `netbird status` на машине>)
- SSH-алиас: `<имя Host из ~/.ssh/config>` (если есть; тогда вход — `ssh <алиас>`)
- ОС / SSH-сервер: `<из баннера>`
- Транспорт: ssh | winrm | SSH-FS | туннель
- Пользователь: `<имя>`  (тип: локальный | MSA | доменный)
- Ключ (ssh): `<путь к приватному ключу>` на `<какая машина им владеет>`;
  публичная половина — в `<authorized_keys / administrators_authorized_keys>`.
  Для winrm — id учётных данных в хранилище winmesh (`Credential` в `hosts.psd1`).
- Root / оболочка (если важно): `<путь>` / `<cmd|powershell|bash>`
- Команда входа (копипаст) — та, что подходит транспорту:
      ssh <алиас>                                # ssh, если есть алиас
      ssh -i <ключ> <user>@<адрес>               # ssh без алиаса
      Invoke-WinMeshCommand <имя> { hostname }   # хост в hosts.psd1 winmesh (ssh или winrm)
      <клиент: хост, порт, пользователь, ключ, корень>   # SSH-FS, туннель
- Особенности этой цели: <что здесь нестандартно; напр. «NetBird ошибочно
  держит пир <имя> на другом IP — не использовать»>.
```

Запись должна позволять войти **без чтения переписки** — только по ней.

## Ловушки (симптом → причина → лечение)

| Симптом | Причина | Лечение |
|---|---|---|
| `ssh`/клиент **висит бесконечно** | TCP не доходит (не тот адрес, закрыт порт, оверлей не поднят). Отказ по ключу пришёл бы мгновенно. | Менять адрес/достижимость, не ключ. |
| `Permission denied`, хотя ключ верный, а баннер `OpenSSH ... Ubuntu` вместо Windows | Это **не та машина** (пир указывает на чужую ОС). | Взять адрес из самоотчёта цели; сверить баннер. |
| WinRM `Connecting ... Access is denied` | Канал дошёл, учётку отклонили. | Чинить учётку/пароль, не сеть. |
| MSA-аккаунт не пускает по WinRM даже со свежим паролем | Облачный пароль Microsoft-аккаунта не работает для сетевого NTLM. | Локальная учётка. |
| `New-LocalUser`/`Set-Service : Access denied / requires elevation` у админа | UAC-урезанный токен. «Админ» ≠ «повышен». | «Запуск от имени администратора»; проверка `([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)` → `True`. Не строкой `'Administrators'`: на локализованной Windows она падает или врёт `False`. |
| `Set-Item WSMan:\...\TrustedHosts : Access is denied` | Правка клиента WinRM требует повышения. | Elevation. |
| Ключ верный, но `Permission denied (publickey)` для админ-входа Windows | Админ-ключ читается только из `administrators_authorized_keys` с ACL Admins+SYSTEM. | Класть туда + `icacls <файл> /inheritance:r /grant "*S-1-5-32-544:F" /grant "*S-1-5-18:F"`. Группы — по SID, не по имени: на локализованной Windows группа называется иначе (`Администраторы`), а на доменной машине без связи с DC поиск имени падает. |
| `Permission denied`, хотя ключ верный и раньше работал; на консоли «The referenced account is currently locked out» | Учётка Windows **заблокирована** политикой неверных входов, и sshd отклоняет даже верный ключ, пока блокировка действует. Источник часто не человек, а программа, пробующая вход с пустым или чужим паролем (на одной машине: запуск полного Chrome со свежим профилем, один неверный вход на запуск). | Не повторять попытки. Проверить `Lockout` через `Get-CimInstance Win32_UserAccount`, затем `net accounts` (там порог и срок блокировки) и журнал Security (события 4740 и 4625, поле «процесс»). Срок блокировки читать из `net accounts`, а не предполагать: значение 0 значит «до разблокировки администратором», тогда ждать бесполезно, нужен админ с консоли или из домена. Источник убрать. |
| `Permissions for '...key' are too open ... ignored` | Проверка прав ключа — относительно запускающего пользователя. | Тестировать под той же учёткой, что и в работе. |
| После смены сети клиент рвётся (`ETIMEDOUT`, `Connection lost before handshake`) | NetBird переустанавливает пир после смены Wi-Fi/адреса. | На клиенте: `netbird down; netbird up`; дождаться `Connected`, проверить `Test-NetConnection <server> -Port 22`. |
| Новая локальная учётка Windows **появилась на экране входа** | По умолчанию все локальные учётки видны в выборе при загрузке. | Скрыть (не отключая): реестр `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\SpecialAccounts\UserList`, DWORD `<имя>`=`0`. Для SSH учётка продолжит работать. |

**Сквозной принцип:** при потере удалённого доступа не подбирай вход удалённо —
если есть консольный/RDP-доступ, настрой локально один раз. Почти все трудности
выше — это трудности именно *удалённого* входа.
